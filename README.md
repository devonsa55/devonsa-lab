# MCP Multi-Surface Demo

> **One MCP tool call. Two native renders.**

**Live:** [lab.devonsa.work](https://lab.devonsa.work)

A working demo of one idea: an agent should return a small, constrained, structured payload, and each product surface should render it in its own design language. The agent never needs to know how a surface looks.

It uses the **Model Context Protocol (MCP)** end to end. A real MCP server exposes a tool, a real MCP client calls it over Streamable HTTP, and the structured result renders into two deliberately opposite surfaces side by side.

This is a personal project. All merchant data in it is invented.

---

## What's real and what's simulated

| Part | Status |
|---|---|
| MCP server exposing `get_merchant_insight` | **Real.** `app/api/mcp/route.ts` |
| MCP client calling it over Streamable HTTP | **Real.** Server-side, `app/api/call-tool/route.ts` |
| Insight content | **Real when a Gemini key is configured**, generated by Gemini Flash. Otherwise it comes from built-in fixtures. |
| Output validation | **Real.** Every payload is validated against a Zod schema before it leaves the server. |
| Rate limiting | **Real.** 12 requests/min per IP, with `429` and `Retry-After` headers. |
| Wire protocol panel | **Real.** It shows the actual JSON-RPC request and response of the last call. |
| Latency readout | **Measured**, but it includes the timeline animation (about 1.3s), so it reads high. |
| Tokens and cost readout | **Estimated** from a formula, not read from the model's usage metadata. |
| "Simulate a failure" chips | **Simulated in the browser.** They play the timeline and stop at step 3 with a canned message. They don't trigger the server's real error paths. |

If Gemini errors or times out, the server falls back to a fixture and prefixes the detail text with the API error. If the whole request fails, the browser falls back to a local fixture. Either way, the surfaces keep rendering.

---

## What it demonstrates

- **A constrained payload is a design decision.** The schema caps lengths, item counts and chart types, so every surface knows what it might receive and can plan for it.
- **One payload, two native renders.** `MerchantCenterCard` is quiet and editorial. `AdsBanner` is bold, geometric and color-blocked. The component names echo the kinds of product surface they imitate in tone. They aren't copies, and neither uses any real brand assets.
- **The payload is inspectable and editable.** Edit the JSON, change `visualization.type`, and both surfaces re-render instantly. The raw MCP request and response sit one click away.
- **Failure states were designed, not left to chance.** The timeline shows where a run stops, what the error says and what the user sees instead of a result.

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                      Client Browser                         │
│   - Presets, query box, widget override                     │
│   - Protocol timeline, latency / token / cost readout       │
│   - MerchantCenterCard (Surface A) · AdsBanner (Surface B)  │
│   - Editable JSON · raw MCP wire panel · specs panel        │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTP POST /api/call-tool
                               ▼
┌─────────────────────────────────────────────────────────────┐
│             Next.js Server-Side MCP Client                  │
│               app/api/call-tool/route.ts                    │
│   - IP rate limit (12/min), request validation (Zod)        │
│   - @modelcontextprotocol/client over Streamable HTTP       │
│   - Calls tools/call 'get_merchant_insight'                 │
└──────────────────────────────┬──────────────────────────────┘
                               │ Streamable HTTP (MCP)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                   MCP Protocol Server                       │
│                   app/api/mcp/route.ts                      │
│   - mcp-handler (createMcpHandler), tool: get_merchant_insight │
│   - Gemini Flash (flash-lite, then flash), 8s budget each   │
│   - Validates output against the Zod schema                 │
│   - 15-minute in-memory cache; fixtures as the last fallback│
└─────────────────────────────────────────────────────────────┘
```

### Why the MCP client lives on the server

1. **Protocol authenticity.** A server-side client connecting over `StreamableHTTPClientTransport` means the app makes a genuine MCP exchange, not a mock.
2. **Secrets stay private.** Model API keys never reach the browser.
3. **Stateless transport.** Streamable HTTP needs no session store, so it runs on serverless platforms like Vercel.

## The tool

**Endpoint:** `/api/mcp` · **Tool:** `get_merchant_insight`

**Input**

```json
{
  "merchant_id": "string (max 64)",
  "focus_area": "inventory | pricing | trend",
  "visualization_type": "auto | trend_line | bar_comparison | progress_gauge | breakdown_distribution",
  "query": "string (max 250), optional",
  "category": "string (max 64), optional",
  "scenario": "string (max 250), optional",
  "time_horizon": "string (max 32), optional"
}
```

**Output**

```json
{
  "headline": "string (max 120)",
  "detail": "string (max 250)",
  "metric": { "label": "string", "value": "string", "trend": "up | down | flat" },
  "visualization": {
    "type": "trend_line | bar_comparison | progress_gauge | breakdown_distribution",
    "title": "string (max 60)",
    "series": "number[] (trend_line)",
    "categories": "{label, value, formattedValue?, highlight?}[] (bar_comparison, max 6)",
    "gauge": "{current, target, unit?, status?: safe | warning | critical} (progress_gauge)",
    "distribution": "{label, percentage, colorHint?}[] (breakdown_distribution, max 6)"
  },
  "chart": "number[], kept for backward compatibility",
  "action": "string (max 40)"
}
```

Four widget types is a deliberate limit. A small, fixed vocabulary keeps every surface's job tractable and keeps the model's output checkable.

## Known limitations

- The response cache and rate limiter are **in memory**, so on serverless hosting each instance has its own. This is fine for a demo and wrong for production.
- Failure chips are simulated, and their canned messages are illustrative. The "60 calls/min" in the 429 message is not the real limit, which is 12/min.
- Token and cost figures are estimates.
- When no Gemini key is configured, the content is fixtures, and the app works the same way.

## Run it locally

**Prerequisites:** Node.js 20+, and optionally a Gemini API key from [aistudio.google.com](https://aistudio.google.com/).

```bash
npm install
```

Create `.env.local`:

```
GEMINI_API_KEY="your_key_here"
```

The key is optional. Without it, the demo serves deterministic fixtures.

```bash
npm run dev
```

Open <http://localhost:3000>.

## Deploy to Vercel

1. Import the repository at [vercel.com/new](https://vercel.com/new).
2. Add `GEMINI_API_KEY` under Environment Variables (optional).
3. Use Node.js 20.x or 22.x.
4. Deploy. The MCP endpoint is served as a serverless route.

## Design notes

`design_handoff_mcp_wrapper_restyle/` holds the written handoff for the page's visual system: tokens, type, states and interactions. It's the spec used to restyle the demo's wrapper chrome. The two rendered surfaces are intentionally left unrestyled so they stay opposite.
